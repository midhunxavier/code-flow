# Team patterns

Start with an Agent conversation. Enable AI team to let a coordinator build and adapt a plan when the task needs collaboration. Open Advanced to choose reusable built-in workflows such as Fix & review, Plan → Build → Review or a Review council, or to design and save a versioned template. Fixed workflows retain the execution and verification behavior described below.

## Team patterns

| Pattern | Roles | Flow | Reach for it when |
|---|---|---|---|
| **Team** (Auto team) | coordinator, generated workers, independent reviewer | Propose and approve a team → ready-task scheduling → addressed questions and bounded revisions → integrate, check, review and repair | You want code-flow to choose the team and workflow; see [Auto team](auto-team.md) for communication, memories, budgets and recovery |
| **Fix & review** | builder, reviewer | Build → check → independent review → bounded fixes and re-checks | A focused change or issue that needs independent review without a separate planning turn |
| **Plan → Build → Review** | planner, builder, reviewer | Plan (read-only) → implement → **check** (the builder fixes it first if it fails) → independent review against the task, with the plan as context → code-flow runs the reviewer's tests → the builder fixes what blocks → re-check and re-review, up to *N* rounds | Most features and bug fixes. Cross-vendor review catches what a model misses in its own work |
| **Review council** | reviewers (1+), chair | Reviewers review the PR's or branch's changes independently, read-only → code-flow runs the tests they show bugs with → the chair merges the findings without knowing who wrote what. Findings rank by severity, then confirmed before the rest, then by how many reviewers raised them | Reviewing a PR before merging. Nothing is changed or posted without you |
| **Agent** | agent | One agent works in its own workspace → you reply in the same session. Agent conversations do not automatically commit or run checks; ask the agent to test its changes. Explicit managed runs checkpoint and check the completed work | Quick changes, questions and exploring, where a team is more than the task needs. Start a team from its result when you want a second opinion |

Earlier versions had more fixed workflows: Loop until green, Best-of-N race, Debate → Synthesize → Build, Supervisor → Workers and Test-first. Runs made with them stay in your history with their steps and results. They can't be resumed or run again, and an automation, queued run or saved template that names one says so instead of starting: use Auto team for that work.

Every pattern works with any mix of agents. A good default is to have a **different vendor review** than the one that wrote the code.

**Auto** in a role picks an installed agent when the run starts. It skips plans that are at 90% or more of a usage window or recently hit a limit, until the limit resets (Claude reports its windows; the others report only when they're limited), and for 15 minutes a CLI that turned out not to be signed in. Once agents have a few finished runs in a repo, it prefers the one whose code passed the check most often there. A role that weighs others' work (a reviewer) gets a vendor that didn't do that work when one has room, and an Auto role whose work is weighed avoids a checker you picked yourself. The pick and the reason are written to the run's activity log. Quota is saved, so a restart remembers which plans are out.

Review verdicts and team plans are **schema-constrained**: `claude --json-schema`, `codex --output-schema` and `agy --json-schema`. An answer that still doesn't fit gets one retry in the same session, and then the run **fails**: an unreadable review is never treated as approval.

Roles that weigh someone else's work are filled the same way in the composer. Unless you pick one yourself, it fills each with a vendor that didn't do that work, and the log warns when a run has one agent doing both:
- Fix & review: the reviewer is a vendor other than the builder's.
- Plan → Build → Review: the reviewer is a vendor other than the planner's (and the builder's, when a third is installed). A reviewer that shares the planner's view lets a wrong plan through, so it's told to judge the change against the task, with the plan only as context.

For the same reason, reviewers are anonymous to a review council's chair (*Reviewer A/B…*).

## Checks, loops and limits

Managed workflows coordinate the loop around agents. Agent conversations preserve working files and leave commits and tests to the agent; their configured check is used for merge validation and when an AI team verifies the work. Verification profiles are inactive until a team or managed workflow runs.

- **Done when:** a check command such as `npm test`, `pytest` or `cargo test`. It's auto-detected from the repo and editable per repo.
  - Python projects locked with uv or Poetry get their own environment, since system Python doesn't have their packages: with `uv.lock`, setup `uv sync` (`uv sync --all-packages` in a uv workspace) and check `uv run --no-sync pytest -q`; with `poetry.lock`, setup `poetry install` and check `poetry run pytest -q`. When the pytest config lives only in `tests/` (a workspace member of its own), the check runs from there. The composer says what it detected from.
  - **Managed workflows run it automatically** after each change, in that worktree, and feed the failing output back to the agent.
  - Loops end on that evidence, not on an agent saying it's done. Every check shows in the run's steps with its output.
  - Fix & review and Plan → Build → Review: reviewers only see code that passes.
  - Managed workflows: a passing result is proven fail-to-pass (see below).
  - When a run finishes but the check still fails, the run is shown as a warning, not a success.
- **A check that can't run isn't a failing check.** Some failures say the environment is wrong, not the code: the command isn't installed (exit 127), Python has neither pytest nor the project's package, pytest can't load `conftest.py` or collects nothing (exit 4 or 5), or a check in a Docker container can't start because Docker's daemon isn't running. With a verification profile, the same holds when every required gate that didn't pass couldn't run.
  - When the run's first check fails like that, code-flow runs it once more on the base commit, in a throwaway checkout (with your setup). If it fails the same way there, the change isn't to blame.
  - The check is then set aside for the rest of the run: no "Fix failing check" rounds (agents would only rewrite the test setup to get around it), and later checks are skipped.
  - The review still runs, and the reviewer is told nothing was tested. The verdict stays unknown instead of failing.
  - The log, the result card, the inbox and the phone view say *The check can't run here: \<first error line\>. Set `setup` and `check` in .codeflow/config.json*.
  - If the check runs on the base commit, the change broke it, and it's a failing check like any other.
- **A pass only counts if the tests are still the tests.** After every change, code-flow looks for edits that make a check pass without fixing anything:
  - deleted test files, and test files renamed to a name the runner doesn't pick up (`parse.test.ts` → `parse.ts`);
  - added `.skip`, `.only`, `xit`, `it.skipIf(…)`, `test.runIf(…)`, `test.skip.each(…)`, `test.fails`, `this.skip()`, `{ skip: true }`, `@pytest.mark.skip`, `pytest.importorskip`, `t.Skip()`…; in Python and JS/TS, not inside a string or comment (a test of a guard against skips may write one into a fixture);
  - test files that lost assertions;
  - a changed test config or CI workflow, including the runner's settings in a file shared with the rest of the project: pytest's `[tool.pytest…]` tables in `pyproject.toml`, and the `jest`, `vitest`, `mocha` or `ava` settings in any `package.json` (`addopts = "--deselect …"`, `testPathIgnorePatterns`…). The rest of those files (dependencies, other tools' settings) isn't flagged;
  - a changed `scripts.test` (or whichever script the check runs);
  - fewer tests running than before, read from the runner's summary. Each result branch keeps the counts of its check (the first and the latest, and at which commit), so a follow-up after the run compares with how many ran before its change.

  If git can't show the change, that is reported too (*couldn't verify test integrity*), as a serious issue: not being able to look isn't the same as finding nothing.

  What happens next depends on the pattern:
  - Fix & review, Plan → Build → Review and Auto team: the changes go to the reviewer, who raises each as an issue (so it blocks approval) unless the task needs them.
  - PR follow-through: nobody reviews these fixes before they're pushed, so one that touches the tests at all isn't pushed: any of the changes above, not only the serious ones (a changed CI workflow or test config, a skip or an assertion fewer). The watch hands it to you instead.

  Every flagged result shows **⚠ Changes to tests to check before merging**.
- **A pass should prove the change (fail-to-pass).** A check that passes with the change might pass without it too, and then it shows nothing about the change. So once a result's check passes, code-flow proves it:
  - it puts the change's tests onto the base code, in a checkout of its own (set up once per run): the test files, their fixtures and snapshots, and the runner's settings (`jest.config.*`, `conftest.py`, `pytest.ini`…). A test file the change deleted is deleted there too. When the change also adds or updates dependencies (`package.json`, `uv.lock`, `go.mod`…), those files come along and setup runs again, so a package only the change adds can't make the tests fail there as if they needed the change's code;
  - it runs the check there. **It should fail**: then at least one test needs the change, and the step reads *Fails without the change, as it should*. A test that imports code only the change adds fails there too, but only because it can't load (an import, collection or build error), which shows the code is there, not that it works: when that is the only way it fails, the result is a **weak proof**. A test that fails on what it checks (an assertion, an expected value) is full proof, also when another can't load;
  - if it passes there as well, the result is **not proven**: no test fails without the change. A run that never reached the tests (no test runner, nothing collected, setup failed, a timeout) proves nothing either way and says so.

  When a fix makes a failing check pass, the tests that failed before are the proof, and no new test is needed. When the check already passed before any change (a new feature, say), only a new test can prove it. What happens next depends on the pattern:
  - Builders are told up front that their tests will run on the original code (Fix & review, Plan → Build → Review, Auto team's workers).
  - Fix & review and Plan → Build → Review: before review, the builder is asked once for such a test. If the check then fails and the fix attempts don't help, code-flow undoes the new test, so asking for a proof never costs a green result. The reviewer sees the proof either way, and is told to ask for a test when it's missing.
  - Review council: with a check, code-flow runs it on the PR's changes and proves them against the code the PR started from, and every reviewer sees both. The proof goes into the review you can post.
  - Managed Agent runs: the result is proven and the proof reported; nobody is asked for a test. Interactive Agent conversations do not run this automatic proof cycle.

  Each result shows **✓ Proven: a test fails without this change** (with how it fails), **⚠ Weak proof** (the tests fail without it only because they can't load), or **⚠ Not proven**. Reviewers are told which. Insights counts proven results per pattern, out of all the proven, weak and unproven ones. A proof costs one more run of the check (plus setup once per run). Turn it off for a repo with `"prove": false` in `.codeflow/config.json`.
- **Review findings are checked, and only what blocks holds approval back.** A reviewer's word is an opinion: a false positive costs a fix round, and the builder can't answer it. So in Fix & review, Plan → Build → Review and the Review council, a reviewer rates each issue high, medium or low, and shows a bug with a *repro*: a test file (its path and whole contents) that fails on the result because of the bug, a plain test-runner command that runs it, or both. A command alone can run tests that are already there.
  - code-flow writes the test into a checkout of the result's current commit, apart from the builder's worktree, and runs it with the reviewer's command, or else the run's check. That checkout is set up once per run, and again only when a file that says which dependencies to install changes (`package.json`, `uv.lock`, `go.mod`…). It's the reverse of a fail-to-pass proof: there the tests should fail without the change; here the reviewer's test should fail with it.
  - The step reads *Fails: the problem is there* or *Passes: a false alarm*. A finding is **confirmed** (its test fails), **not confirmed** (it passes: a false alarm), or **unconfirmed** (no test came with it). Sometimes code-flow can't tell: the test runner didn't start, it timed out, the check already fails on that code without the test, or the test never ran: as many tests ran with it as without (with the reviewer's own command, code-flow counts once more without the test, unless the command names it), no test ran at all, or the runner doesn't say how many ran and nothing in its output mentions the test.
  - Only a plain invocation of a known test runner runs, and only a file named like a test goes in, so a repro can't replace the code it's about. The test is never written through a symbolic link in the code under review, so a PR's tracked link can't send it outside the checkout. At most 6 run per review; low issues aren't run.
  - **Approval goes by the findings, not the verdict word.** High and medium issues block; low ones are suggestions. A false alarm never blocks. A high-severity issue claims a bug, so it blocks only when its test fails, or when code-flow couldn't run the test it came with. Without a test it's marked unconfirmed and doesn't block; reviewers are told to rate a problem no test can show medium. So a reviewer that approves with a confirmed bug doesn't approve, and one that requests changes over false alarms and suggestions does.
  - Findings that block go back to the builder. Confirmed ones come with the reviewer's test and how it fails: the builder makes it pass and adds it (or one like it) to the change. The ones no test shows it fixes, or disputes with evidence (a test it ran, the code that handles it) instead of changing code. False alarms and suggestions are listed as needing no change. In the next review the reviewer sees the builder's answer, and keeps a disputed bug only with a repro that fails.
  - Each run of a reviewer's test is journaled, so a resumed run replays it instead of running it again, and the same test on the same commit runs once.
  - Review council: each reviewer's tests run before the chair merges the reviews, and the chair sees what each one showed and keeps a finding's repro. Findings rank by severity, then confirmed before the rest (false alarms last), then by how many reviewers raised them. The council's verdict goes by the findings too: it requests changes when a finding blocks, and approves when none does, whatever the chair said. Nor can the chair drop a finding a test confirms, or rate it lower: code-flow puts it back as its reviewer raised it, marked *Restored by code-flow* in the review, and the log says so. The review you can post says how each finding was checked.

  The result shows the latest review's findings, each marked **✓ Confirmed** (with how it fails, and the test), **✗ Not confirmed** (a false alarm), **⚠ Unconfirmed** or *couldn't run*, and which block. The summary counts unconfirmed high-severity claims and false alarms.
- **Parallel work stops together:** when a pattern runs branches side by side (a council's reviewers, say) and one fails, the other branches are stopped too. The run ends once every branch has, so no agent keeps running after it, and Stop and the slots stay accurate.
- **What agents see:** long diffs keep whole source files first, put lockfiles and generated files last, and list any file that didn't fit with the command to read it. A long check log keeps the lines around each failure plus the runner's summary, not just the tail. Agents also get the repo's own conventions files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, …), since each CLI otherwise reads only its own. They're also told about problems reviewers raised in more than one earlier run in that repo (turn this off with `"learn": false`).
- **Limits:** every run stops at a maximum number of minutes or agent steps (720 minutes and 500 agent steps by default). The clock doesn't run while the run waits for you (a checkpoint), or only waits for a free slot (see *One machine, many runs*). Minutes must be a finite number from 1 to 1440; agent steps must be an integer from 1 to 1000. The budget picker beside the run summary offers 200 calls / 4 hours, 500 calls / 12 hours, and 1000 calls / 24 hours, plus custom limits. Selecting a preset also updates the chat’s AI team allocation and any inherited retry call ceiling; optional token and cost ceilings stay as set. Existing saved budgets are retained until you change them. Invalid explicit limits block starting and preserve the draft. A stopped run keeps its work: each worktree with changes is listed as "Work so far".
- **Plan usage:** if a CLI says its plan is out of usage, the run stops instead of failing, so you can resume it once the plan resets. Auto skips that plan until the reset time the CLI gave (or the reset times it reported before). A CLI that isn't signed in fails the step with a message saying so, and Auto skips it for a while.
- **Retries:** a turn that fails for a passing reason (overloaded, rate-limited, a network error, a CLI that stalled) is retried after 20 s, then 60 s, with its agent slot free meanwhile. A write turn picks up where it stopped: it continues its own session, or, without one, starts over from the worktree as the step found it, so a retry never redoes the work on top of half of it. Whether a failure is passing comes from the CLI's own error type; for a CLI that gives none, from its message (an HTTP status counts only with words around it, such as "status 503", not a bare 500 in a test log).
- **One machine, many runs:** at most 6 agent CLIs and 3 checks run at once across all runs (`CODEFLOW_MAX_AGENTS`, `CODEFLOW_MAX_CHECKS`). Others wait their turn, and the step says so. The wait doesn't count against the run's time limit (a sweep's runs queued behind each other don't run out of time before they start), unless another of its steps runs meanwhile.
- **Stopping really stops:** each agent CLI and each check runs in its own process group. Cancelling, a time limit or the CLI exiting stops everything it started, such as a dev server it left in the background, and escalates to SIGKILL if needed.
- **Setup:** an optional command, such as `npm ci` or `uv sync`, that runs once in every new worktree before the agents start. code-flow runs it itself, outside the agents' sandboxes, so dependencies are installed even though Codex has no network in Standard mode. A worktree is marked as set up (in its own git folder, not in its files) once setup finishes; one whose setup never finished, because code-flow stopped during `npm ci` say, is set up again when a resumed run reuses it.

Reviewers may suggest their own test command with a repro. code-flow only runs it if it's a plain invocation of a known test runner, with no shell operators. Otherwise it falls back to your check.

> **Security:** a check runs the agents' code (tests, scripts) on your machine, outside Codex's and agy's sandboxes, as your CI would. Use code-flow on repos and tasks you trust, or run checks in Docker (see [Automations](automations.md#isolation)) or code-flow itself inside a container or VM. More in [Security](security.md).

Adding your own pattern: see [Architecture](architecture.md#adding-a-pattern).
