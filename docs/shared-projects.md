# Shared project accounts

Create a local account and grant roles only for the projects that person should see. Review the role table before allowing contributions or maintenance, and revoke access when it is no longer needed.

## Share board access

The server owner can create local accounts and assign one of four project roles; each role includes everything the roles before it may do. A signed-in shared account sees one page, the project's [team board](team-collaboration.md), and nothing of the owner's runs. A **viewer** reads the board, its tasks, checkpoint manifests and discussion, and their own inbox. A **reviewer** also comments on tasks, @mentions teammates and records a review (approve or request changes) against a checkpoint. A **contributor** also creates and owns tasks on the board and runs them on their own computer with their own agents. A **maintainer** also assigns any task owner, defines a project's repository keys, deletes board tasks and checkpoints, revokes runners, cancels hand-overs and approves instructions to agents; accounts and roles stay with the owner. The full role table is in [Team collaboration](team-collaboration.md#set-up-the-team-server).

Shared accounts cannot open runs. Run history, results, diffs, file-review coverage, result exports and the run comment thread belong to the owner; a shared session that asks for them gets 403 "This operation requires the Code Flow owner". Earlier versions gave shared accounts a **Results** page where viewers read results and reviewers recorded file reviews and comments. That page is gone. Comments recorded there are kept: the owner still reads and answers them under **Changes → Comments** on the run page. Those comments never enter an agent's prompt or resume work.

The owner retains administration and run controls. Project roles alone do not allow users to start or resume runs on this server, approve agent/tool requests, send agent notes, run checks/setup/services, change repository files, choose Docker images or authentication volumes, use terminals, merge/push/post to GitHub, edit private memory/conventions, configure integrations, manage accounts or inspect global filesystem/settings/quotas. Project assignment is not an operating-system sandbox. An explicit owner grant under Settings → Connections → Share access → People allows a contributor to queue their own team tasks on the host through the dedicated [host execution queue](team-collaboration.md#let-teammates-run-tasks-on-the-host). This delegates host execution authority to trusted teammates; it does not provide an operating-system sandbox. Generic run and shell APIs remain owner-only. A separate [interactive terminal grant](team-collaboration.md#give-trusted-teammates-an-interactive-terminal) lets a trusted contributor open their own shell on the host. That shell has the host OS user’s authority, including file changes and access outside the project; the shared API restrictions do not sandbox terminal commands.

The shared dashboard uses its own bootstrap requests so shared users do not load the normal composer's global health/configuration APIs. Every address opens the board (`#/team`), a task or the people page. The dashboard holds one event stream (`/api/team/events`), reloads on its frames and loads the bell's unread count once with the page; it sends no periodic request of its own, so an idle dashboard does not renew its session by polling. An open interactive terminal has its own authenticated output stream. Board tasks, events and inbox items are filtered by current project membership on the server; what the board shows of a linked computer's work is described in [Team collaboration](team-collaboration.md).

## Authentication and storage

Accounts live in private `CODEFLOW_HOME/shared-accounts.json`; the server never returns password hashes or session hashes. Passwords require at least 15 characters and at most 1024 UTF-8 bytes, without normalization or truncation. Built-in scrypt uses a fresh 16-byte salt, a 32-byte key and parameters `N=131072, r=8, p=1`. Verification compares keys in constant time and performs a dummy derivation for unknown accounts. At most two password derivations run concurrently; a full queue is refused. Login attempts have bounded global, socket-address and username rate limits.

Sessions use 32 random bytes and store only SHA-256 hashes. They expire after 12 hours or 30 minutes idle; each account retains at most eight sessions. Role/display-name/enabled/password changes and owner revocation invalidate every session for the account. Session activity extends idle time in memory; a restart can expire a session earlier than its last activity. Revoked identities must lose open streams immediately. Corrupt or symbolic account storage disables shared authentication without overwriting the file; the owner's printed recovery-token link remains available.

Network sign-in and authenticated shared requests require actual HTTPS, independently of the phone development override. Cookies are HttpOnly and SameSite=Strict, Secure on HTTPS. The server validates Host/Origin and mutation request type. Shared cookies are distinct from owner and phone sessions. An explicit valid owner bearer credential on the local listener takes precedence; otherwise a valid shared cookie takes precedence. The network listener refuses local owner bearer credentials and recovery links; use its separate phone pairing or shared sign-in. Shared sign-in clears the owner browser cookie, and an explicit local owner recovery link clears the shared cookie. Account creation disables first-browser owner claiming.

Backup and restore omit account/session stores, including older archives. Recreate accounts and assign project roles deliberately after restoring. Human collaboration comments can be retained with application data but convey no authentication authority.

## API and enforcement contract

`POST /api/auth/login {username,password}` sets the session cookie. `GET /api/auth/self` returns only the current public identity; `POST /api/auth/logout` revokes the current session. Owner administration uses `GET/POST /api/accounts`, `PUT /api/accounts/:id` and `POST /api/accounts/:id/revoke-sessions`. Every mutation carries the exact current account-state `revision`; stale updates fail with 409 while preserving the existing state. Project IDs must be validated against the current project store before assigning roles.

The owner's run comment thread uses `GET /api/runs/:id/collaboration` and `POST /api/runs/:id/collaboration {branch,expectedHead,text}`. The server resolves an owned result branch; the store rejects a changed commit. Comments are bounded to 4000 characters and 200 entries per run, with immutable author/time/commit metadata. Both routes are owner-only.

`canonicalSharedPath` checks the original request target before URL normalization, accepts the versioned `/api/v1` alias, and rejects encoded separators, double encoding, dot segments, empty segments and extra ambiguous suffixes. A shared session is dispatched only to the team board (`/api/team/*`), host queue (`/api/host-execution`) and team terminal (`/api/team-terminals`) route tables; every other route, known or new, answers 403 and never falls through to an owner handler. Global authorization must run before all API/workspace handlers, and resource authorization must precede Git/filesystem operations. Public pairing/webhook routes retain separate secret capabilities and do not inherit a shared user's project roles.

The account, path and comment-store tests cover hash-only storage, modes, exact revisions, role escalation refusal, revocation, expiry, bounded login work, malformed paths/aliases and durable commit-anchored comments. `test/e2e/shared-projects.e2e.ts` signs shared accounts in and checks that every run route answers 403, that the dashboard opens on the board, and that the owner still reads earlier reviewer comments.

The password parameters and authorization model follow the [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) and [Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
