# Agent mode implementation and validation

Date: 2026-10-22. Branch: `codex/agent-mode-parity`. Base: `origin/main` at `8a97ced`.

## Delivered behavior

- Agent and Team are the visible mode names; saved `solo` and `auto-team` IDs remain compatible.
- Claude stream-json partial blocks and Codex app-server deltas update identified transcript items. Completed snapshots replace partial content, preserving tool ordering without duplicate answers. Failed or cancelled turns keep their output and accept a next message.
- Agent chats retain native sessions and leave commits, checks, and PR operations to the agent under the chosen permissions. Explicit task runners, remote workers, code-host reviews, and their retries retain automatic checkpoint/check behavior through `checkpointOnFinish`.
- Provider changes open sibling tabs sharing the workspace. Cross-provider context includes visible user/assistant history and attachments; native session IDs are never transferred across providers. Idle same-provider forks use native fork APIs. Active-source forks carry completed visible context. Files are the current shared files, not a historical rewind.
- Writer turns sharing a workspace are serialized. A cancelled queued writer cannot release the next writer ahead of the active one. Independent Claude/Codex side chats use read mode and can answer while the main agent runs; cleanup never restores an old snapshot over concurrent main-agent changes.
- Drafts survive tab navigation and reload. Tabs restore from durable relationships. Main-chat scroll position is retained, and side-chat provider changes stay in the side panel.
- Claude tool approvals and native questions, plus Codex requests for user input, route through the scoped approval inbox. Expiry and cancellation do not fabricate an answer. Agent chats retain the provider's configured integrations; Team restrictions remain enforced.
- Both native providers receive a turn-scoped MCP bridge for Chrome navigation, accessibility snapshots, grounded form interaction, screenshots, tabs, and macOS computer screenshots/clicking/typing/keys/scrolling. Credentials expire with the turn. Computer actions need Full access or an explicit action approval, existing OS permissions, and a fresh screenshot. Foreground-app changes reject stale actions.
- The macOS package compiles and signs the computer helper alongside the app; npm/source installations compile its bundled Swift source once and cache it. Chrome processes close with the bridge and after idle expiry.

## Supported boundaries

This implements the observable core conversation workflow using public provider interfaces. It is not a claim of complete feature parity with every desktop release. Direct Codex desktop inspection was unavailable; the implementation uses its documented app-server protocol. REA was not needed.

Built-in browser tools and the in-app Browser panel now use one dedicated Chrome profile per task, shared by its provider tabs; they do not inherit the user's logged-in Chrome tabs. Provider-configured Chrome/MCP integrations retain their own setup and permissions. Native computer tools currently support macOS and its primary display; Linux can use the browser tools or a separately configured computer-use integration. npm/source computer use requires Swift Command Line Tools; the macOS app package includes the compiled helper.

Shared provider tabs require a local workspace. Independent read-only side chats are currently enabled for Claude and Codex; other providers retain their existing transports and are not claimed to pass the live parity suite. Computer actions are not silently enabled when OS permissions are absent. Arbitrary provider-installed tools still follow that provider's permissions rather than inheriting a filesystem sandbox from the MCP bridge.

## Shared browser file uploads and downloads (2026-10-22)

The owner chooses local files with the native picker; authenticated binary streams stage them for that exact Chrome file chooser. Multiple files, binary contents and cancellation work. - A task-level Downloads list shows progress, Save, Cancel and Remove. Regular HTTP attachments and page-generated blob exports use the same Chrome session. Provider forks share the same tab, cookies and download IDs. Existing destination files are not overwritten. Agent paths cannot traverse outside the workspace, follow symbolic links or access `.git`; project file policies and read-only side-chat restrictions apply.

UI downloads stream from disk rather than buffering an entire file into the page. Ordinary file selections accept at most 20 files, 100 MB per file. With folder support added below, the browser retains at most 2,000 staged files / 500 MB per session. Staged files are cleared when Chrome closes. Downloads are limited to 1 GB per file and 100 files / 5 GB per task; removing old downloads frees the task allowance. Ordinary HTML file inputs are supported; folder inputs are covered below. The File System Access API picker remains unsupported. Saving through the agent requires an existing destination folder.

## Selective steering, browser takeover, failover and conflict resolution (2026-10-22)

This update implements the four recovery features listed as outstanding in the preceding section. It preserves the Agent conversation layout. Team work and provider-change history stay in collapsed activity; conflict comparison opens only when requested. Browser ownership controls live in the Browser panel.

- Selective steering resolves explicit assignment/member/file references and includes dependent tasks. It cancels only affected running worker turns, retains partial files and tool-action receipts, and reuses unrelated completed work in the same execution. Requests and scheduler boundaries are journaled; restart replay applies each correction once. Corrections are also authoritative for coordination, final review and repair. Matching is a conservative English lexical rule: ambiguous input targets all tasks. Planning and final verification retain the existing whole-execution recovery path.
- Shared browser ownership now has a cancellable FIFO queue, explicit agent release, 30-second idle expiry, 90-second bounded waits, and human takeover. A takeover acknowledges only after in-flight agent actions settle. Concurrent human requests release together; an explicit takeover remains held until the user releases it. Handoffs require a new inspection. Existing task tabs, cookies and transfer state are retained.
- Coordinator, worker and reviewer calls may fail over within the authorized provider pool. Model settings come from the replacement provider's configured/reported choices; native sessions never cross providers. Quota, permissions, strict review independence, call/time budgets and the model catalog remain enforced. Host-observed tool actions accompany the handoff so the replacement can inspect current state before continuing. If no eligible provider remains, work is preserved and completion is blocked. The advanced opt-out is `providerFailover: false`.
- Three-way reconciliation compares the task baseline, current workspace and verified team result without changing HEAD or the user's index. Clean merges apply automatically. Conflicts preserve both versions and expose keep-yours/use-team/edit choices. Stale comparisons and unresolved markers are rejected. Binary, symbolic-link and oversized content must use an existing version. Configured checks and verification-profile gates run after reconciliation; a failing gate or a workspace change during checking prevents a passing receipt. The old independent review is not represented as reviewing subsequent user edits.

## Resume, final-answer recovery and steering (2026-10-22, latest update)

Explicit Resume now retries the blocked logical provider call using fresh availability. Successful planning and completed assignments remain journaled. Exhausted admission/replacement decisions are invalidated only at the recovery frontier; selected-provider, permission and independent-review requirements remain in force. The latest stopped Team execution can resume from its existing parent conversation, refresh its saved receipt and produce a new lead answer. A refused Resume admission restores the saved turn and retry controls.

The final conversational answer has its own recovery path. If the lead is unavailable after delegation, another selected provider receives the visible conversation and Team receipt without inheriting a foreign native session or repeating the team. The successful provider becomes the conversation provider for the next message. If all selected providers are unavailable, **Retry reply** retries that answer while retaining the completed team. Failed attempts are disclosed under **Show work** rather than rendered as competing answers.

Steering recognizes mixed questions and work constraints, excludes explicitly protected sibling assignments when there is a positive target, and invalidates affected dependents. Pure questions can receive a read-only lead answer while teammates continue. Waiting Team questions use the existing main composer. Progress remains collapsed; Team setup stays behind the existing toggle. Conflict reconciliation reports failed checks and outdated review honestly, with a contextual check-again action; it does not label a changed workspace independently reviewed without new evidence.

Antigravity now has the scoped live Team mailbox over authenticated HTTP MCP in its isolated executor, as well as read-only side conversations and portable visible history on subsequent turns. Its native shell/browser and ambient MCP configuration remain excluded from the isolated profile. Computer use still requires Full access, and Antigravity does not support interactive per-tool approval prompts.

Shared browser/computer actions record durable intents before execution and completed/uncertain outcomes afterward. Stable operation IDs prevent the same recorded action being repeated after recovery; an uncertain outcome requires inspection. Agent and Team desktop calls use the same ownership queue. Human browser takeover pauses Code Flow's queue and provider watchdog budgets while cancellation remains available. Native provider transports still have their own timeout ceilings. These receipts cover the shared tools; they do not guarantee exactly-once execution for arbitrary native commands or actions retried under a new operation ID.

Browser snapshots now wait briefly for document/fetch activity to settle, with a bounded wait and an explicit pending-request notice. Delayed confirmation and live exactly-once submission checks pass. Navigation and uncertain actions alone cannot satisfy an implementation deliverable; completed effects still require independent review and configured checks.
